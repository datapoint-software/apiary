# Review notes

Decisions made and findings noted while building the milestones without review, for the team to confirm, change or move into the other documents. Each says what was done, why, and what would change it.

## Deviations from engineering.md

- **The admin API uses reflection-based JSON**, not source generation. Mediator maps the actions and serializes their results itself. The replicated state and the access logs use source generation.
- **The UI's API client is written by hand** (`src/web/projects/apiary/src/app/api/api.ts`), not generated from the OpenAPI document. Every action is a `POST /api/<area>/<action>` with a JSON body, so a generator would add little for now. Revisit when the API stabilizes.
- **Component styles are global**, in `@datapoint/apiary-ui`'s `apiary.css`, as the design system ships them, instead of per-component styles. Moving them into components would split the design system's single stylesheet.
- **Expected failures in handlers throw `ActionFailedException`** with an error code and a kind (not found, conflict, unavailable, forbidden, throttled, invalid), mapped to ProblemDetails in one place. Field-specific failures throw FluentValidation's `ValidationException` instead, so they reach the right field.
- **Mediator action names are lowercase with hyphens** (`users.change-role`), because Mediator only accepts those.
- **Apiary has its own small ACME client** (RFC 8555, in `Datapoint.Apiary.Certificates/Acme`) instead of a library. The usual .NET library, Certes, brings BouncyCastle and isn't maintained much; ours is about 300 lines on `HttpClient` and `ECDsa`, behind `IAcmeClient`. Like the join protocol, it's security-relevant code to review.
- **ASP.NET Core Data Protection is registered** by `AddAuthentication()`, though Apiary doesn't use it. Its key ring is kept in memory, unencrypted (`InMemoryKeyRing`), so nothing reaches the disk and no warnings are logged.

## Product decisions

- **Route timeout:** 1 to 120 seconds, 30 by default.
- **Loopback is in the default admin allowlist**, besides the private ranges, so `docker compose` with the admin port bound to `127.0.0.1` works, and so does `apiary users create-admin` from inside the container.
- **Password minimum is 15 characters**, as architecture.md says. The prototype said 12.
- **Sessions last 12 hours**, with no idle timeout yet. They live in the replicated state, so signing out or disabling a user ends them on every replica. Signing in therefore needs a majority of voters; reads with an existing session don't.
- **Signing in has two steps.** The password step changes nothing; the code step starts the session. A short-lived challenge, encrypted with AES-GCM, carries the account between them.
- **Failed sign-ins are throttled per account and IP address**, in memory: free for 3 tries, then 2, 4, 8 seconds and so on, up to 15 minutes. The 5th failure in a row is audited.
- **Requests from other sites to the admin API are refused** using `Sec-Fetch-Site` and `Origin`, besides the `SameSite=Strict` cookie. Same-site requests are refused too, since apps routed by Apiary on sibling subdomains are same-site.
- **`apiary users create-admin` needs `--email` as well as `--name`**, since the email is the sign-in name. It reaches the running server with a token that Apiary writes to `{data}/operator-token`, readable only by its own user, and accepts only over loopback.
- **Users list:** Administrators only, since it lists everyone's email. The audit log stays readable by every role, as architecture.md says.

- **The root key is text, `apiary-root-key-1:` and 32 random bytes in base64url**, so a wrong file (e.g. a password) is refused instead of being used as a key. Keys are derived from it with HKDF-SHA256, one purpose string each.
- **State at rest:** `state/keys.json` holds the data keys, wrapped with AES-GCM by a key derived from the root key. Every log entry and the snapshot are encrypted with the current data key (AES-GCM, with a purpose string as associated data). **The leader adds a new data key every 90 days** (`Apiary:DataKeyLifetime`) in a replicated entry, which every replica adds to its key ring as it applies it; later entries use the new key. Old keys stay in the ring, since older log entries and snapshots still need them, so rotation limits how much each key encrypts rather than retiring keys. The new key travels in the Raft log, encrypted with the previous data key at rest and by TLS between replicas.
- **The generated root key lives in `/keys`**, a separate volume from `/data`, in the image and the Compose file.

- **Automatic certificates renew when a third of their lifetime is left** (30 days for today's 90-day certificates), so shorter Let's Encrypt lifetimes need no change. After a failure Apiary retries in 5 minutes, 15 minutes, 1 hour, then every 6 hours. [ACME Renewal Information](https://datatracker.ietf.org/doc/rfc9773/) isn't used yet.
- **Certificate keys are ECDSA P-256**, and so is the ACME account key.
- **An automatic certificate no route uses is kept for 30 days**, then deleted, so re-adding a route doesn't hit rate limits.
- **HTTP is redirected to HTTPS (308) only once a hostname has a certificate.** Until then the route answers over HTTP, so the first certificate can be requested. No HSTS yet; it should be a per-route choice.
- **`PublicHttpsPort` (443)** is the port used in redirects and in the `alt-svc` header for HTTP/3, since the container listens on 8443 and the port is published as 443. Kestrel's own `alt-svc` header is off, because it would advertise 8443.
- **A TLS connection for a hostname with no certificate is refused** during the handshake. There's no default certificate, so clients without SNI get no HTTPS.
- **Uploaded certificates:** RSA or ECDSA keys without a passphrase, at most 64 KB of PEM each. The chain must reach a root, either publicly trusted or included in the upload, so internal CAs must include their root. The check step shows what the certificate covers before it's added. Each belongs to a project, like routes.
- **The upload dialog uses text areas with "Choose file" buttons** rather than the prototype's drop zones, which the component library doesn't have yet.
- **"Renew now" waits for the result** in the request, which takes a few seconds against Let's Encrypt.

- **Every replica votes.** architecture.md describes voters and non-voting followers with a voter count, but DotNext.Net.Cluster has no non-voting members, so milestone 4 makes every replica a voter. Run 3 or 5 replicas: 3 tolerate one down, 5 tolerate two, and an even count adds no tolerance. Followers would need either a DotNext change or our own state shipping to non-members; decide whether they're worth it before milestone 5's voter replacement.
- **A replica reports healthy while it joins, in Swarm.** architecture.md says the health check passes once a replica has caught up. But `tasks.<service>` lists only healthy tasks, so a replica that waited for its health check before joining could never be found. In Swarm the check passes from start until the replica has joined and caught up, then reflects readiness. The cost: a rolling update may stop the next replica before this one has caught up. With `stop-first` and one replica at a time, a majority stays up; watch this with large states.
- **Membership is by address.** DotNext identifies members by IP address and port, and a Swarm task gets a new address on every restart. A restarted replica announces itself to the leader, which swaps its old address for the new one using the replica's ID (or its node). On a full restart, each replica rewrites its member list from what peers report, using the state and a local history of which replica had which address (`raft/addresses.json`).
- **If replicas restart while there's no majority, the cluster may not re-form on its own.** Each one's member list can then hold addresses the others no longer use. Restarting the whole service fixes it (`docker service scale apiary=0`, then back), which the replicas log as a hint. Tried with two replicas cut off and a rolling update; milestone 5's forced recovery covers what this doesn't.
- **Slot 1 creates the cluster.** It does so only when every peer it can see answers that there's no cluster. If slot 1's volume is lost while the other replicas are down, slot 1 starts a new, empty cluster; the others then refuse to join it ("another Apiary cluster answers") and stop, so it fails loudly rather than mixing states. Recovering means removing slot 1's new volume. Milestone 5's recovery should cover it.
- **Writes during a leader change** wait up to 15 seconds for a leader (in practice 2 to 3 seconds when the leader's node stops). With no leader known for 3 seconds, Apiary answers `cluster.noQuorum` (503) instead of waiting longer.
- **Read your writes.** After a command forwarded to the leader, the follower waits until it has applied the leader's index before answering. A request whose session cookie a follower doesn't know yet makes it check with the leader first (a read barrier, at most 2 seconds), so a session works on every replica right after signing in.
- **The replicas page shows the leader's view.** Followers don't talk to each other in Raft, so a follower asks the leader which replicas it can reach. Without a leader, it shows its own view.
- **Membership mode is a cluster setting**, on the Replicas page (`cluster.update-membership`), automatic by default, so a new cluster always forms on its own. In manual mode a replica Apiary hasn't seen before asks to join and waits; the replicas it asks keep it in memory for a minute after its last try, and the page shows the leader's list. Approving writes its ID to the state, and its next try (every 2 seconds) joins. A replica that leaves cleanly, as in a rolling update or a scale-down, keeps its approval, so updates need no approvals; one removed while missing, or whose volume is new, needs approval again.
- **Missing replicas are removed after 5 to 1440 minutes** in automatic mode (the prototype's range); never in manual mode, where an administrator uses "Remove now". "Remove now" only works on unreachable replicas.
- **A replica that isn't ready answers 503** on the public and admin ports (`cluster.notReady`, and a "starting" page for sites), instead of serving an empty configuration while it joins or waits for approval. The health check still passes in Swarm, as above.
- **A replica removed while it was unreachable restarts** when it comes back and sees that the others have a leader without it, then joins again as a new replica (or waits for approval). Before, it kept serving its last configuration with no leader.
- **The cluster CA rotates in three steps, a day apart** (`Apiary:ClusterCaOverlap`), starting 180 days before it expires (`Apiary:ClusterCaRenewBefore`; it lasts 2 years): the leader adds the next CA, which every replica then trusts; then replicas switch to certificates from it; then the old CA is dropped. Each step is a replicated entry, and each replica swaps its credentials as it applies it, without restarting. A replica that was away for a whole step catches up when it restarts, since joining hands it the current CAs.
- **Replica certificates are renewed 30 days before they expire** (they last 90 days). Before, a replica got its certificate only when it started, so one running for 90 days would have been refused by its peers.
- **Backups are files the administrator downloads**, not copies kept by the cluster. They're sealed with a key derived from the root key (`apiary/backups/1`), so they're as safe as the root key, and a backup can't be opened after the root key is rotated unless the old key is kept. Restoring signs everyone out. Restore is also offered on the setup page, so a lost cluster can be rebuilt from a backup without an administrator.
- **Forced recovery** (`apiary recover --force`, run inside a container) makes that replica the only member of a new cluster, with a new cluster ID and a new cluster CA, and signs everyone out. It refuses while there's a majority, and when a reachable replica has more changes. The old replicas then find the new cluster (every 15 seconds each replica asks the peers outside its member list), move their state to `/data/superseded-<time>/` and rejoin as new replicas. Tried with two of three replicas paused. **Risk:** if the old replicas come back as a majority, they keep accepting writes until they notice the new cluster, at most about 15 seconds; those writes are lost. The archived state is kept, so nothing is deleted, but it isn't merged back either. Clean up the `superseded-*` directories by hand.
- **Replies over 16 KB aren't remembered for retries** (`AppliedRequests`), e.g. a backup export. Retrying such a command runs it again; the ones affected are reads, so it's harmless today.
- **No automatic certificates for `localhost` and `*.localhost`.** Let's Encrypt can't issue them ([RFC 6761](https://datatracker.ietf.org/doc/html/rfc6761)), so asking only filled the logs and the audit log with failures. `.test` hostnames still get them, since Pebble serves them.

- **State changes carry a schema version, for rolling upgrades.** A replica on an older version can't read a change type it doesn't know, and fails to replicate, so a leader on a newer version could break the majority mid-update (found while trying the CA rotation). Replicas now report the schema they understand when they join, and the leader refuses an entry that needs a newer schema than every replica has (`cluster.upgrading`, 503) until the update finishes. Everything is schema 1 for now. **Proposed rule for engineering.md:** after 1.0, a new `IStateChange` type bumps `StateSchema.Current` and gets `[StateSchema(n)]`; changing an existing type's JSON in a way older versions can't read counts as new.

## Security findings to resolve before 1.0

- **Recovery codes are hashed with SHA-256.** They have about 40 bits of entropy, so someone holding both the state and the root key could find them offline. The state is now encrypted at rest, which covers a copy of the state volume on its own; a slow hash would cover the rest.
- **The state log isn't bound to its order.** Each entry is encrypted and authenticated on its own, so someone who can write to the state volume can't forge or change entries, but could drop the last ones or replay a copy of the volume from earlier. Milestone 4's Raft log replaces this storage; bind each entry to its index there.
- **Fixed: Apiary generated a root key whenever none was mounted.** In Swarm it now refuses to start without the secret, as architecture.md says.
- **The common-password list is short**, plus checks for repeated characters and keyboard or alphabet runs. Replace it with a real list (e.g. common passwords of 15 characters or more) before release.
- **The admin port is still plain HTTP**, so the session cookie isn't marked `Secure`. It needs a certificate that internal clients trust; milestone 4's cluster CA could issue one, or an operator could upload one. Decide which.
- **Backups and recovery must not be MCP tools** either (`backups.export`, `backups.restore`, `setup.restore`): exporting hands over the whole state, sealed only by the root key.
- **`certificates.check` and `certificates.upload` must not be MCP tools** (architecture.md: uploading private keys is UI only). Exclude them when milestone 9 maps the actions to MCP.
- **The leader trusts the user a follower forwards.** A forwarded command carries the user's claims. For a session the leader rebuilds the user from the state, but other sign-in types (the local operator token) are taken as sent. Any replica can already read the whole state with the root key, so this adds little, but it's worth knowing when reviewing the cluster port.
- **The join endpoint accepts anonymous TLS** on the cluster port (9445, on the overlay network only). It's authenticated by an HMAC from the root key, with a time window of ±5 minutes, the requester's address checked against the one it claims, and the data keys sealed in the answer. Everything else on that port needs a certificate from the cluster CA. It's security-relevant code to review.
- **Unknown session cookies cost a round trip to the leader** on followers (the read barrier above). The admin port is limited to the allowlist, so only allowed networks can cause it; add a rate limit if that changes.
- **Private keys are plain in memory** on every replica, and encrypted only at rest. That's inherent to serving TLS.
- **"Renew now" audit entries don't record the IP address**, unlike other actions, because the issuer writes its own entries.

## Regulatory findings

- **AGPL section 13.** The UI's "Source" link points to `sources.internal`, which people using a deployment outside Datapoint can't reach. The AGPL requires offering the source to every user who interacts with the software over a network, so the link needs a public URL before release (or a setting for each deployment).
- **Personal data:** the audit log shows email and IP addresses to every role, as the architecture allows, and the audit page says so.

- **Let's Encrypt's Subscriber Agreement.** Apiary agrees to the ACME server's terms of service when it creates its account, on the operator's behalf. Say so in the deployment docs and the Certificates page before release. An `Apiary:Acme:Email`, if set, is personal data sent to Let's Encrypt.

## Known issues

- **Fixed: a snapshot from an older version couldn't be saved again.** System.Text.Json source generation sets an `init` property that's missing from the JSON to null, ignoring its initializer, so a new list in the state was null after an upgrade. New state properties now use a backing field whose getter falls back to an empty value. Watch for this whenever the state gains a property.
- **An interrupted rolling update can leave the member lists out of step**, so the replicas crash-loop. Restarting the whole service (`docker service scale apiary=0`, then back) fixes it, as above.

- **Mediator's known issue (English messages in error responses) is fixed for HTTP** by stripping title and detail in `ProblemDetailsCodes`. It remains for MCP until milestone 9.
- **The public 404 page's colors** are hard-coded rather than taken from the design tokens.
- **Fixed: routes answered 404 after a restart** until the next change, because loading the state didn't signal the proxy. Found while trying milestone 3; it existed since milestone 1.
- **HTTP/3 isn't verified.** Kestrel listens on UDP 8443 and advertises it, but no HTTP/3 client was available to try it. Check with `curl --http3` against a real deployment.
- **Fixed: a certificate lock held by a stopped leader made the new leader loop.** It wrote a state change on every try, and each change woke the renewal check again, about 100 entries a second until the lock expired after 10 minutes. It now checks the lock before writing. The same could happen on a single node after a restart during an issuance.
- **The design system's `> .ap-icon` selectors missed the Angular `<ap-icon>` wrapper**, so banner and toast icons had the wrong colors. They now match both forms. `.ap-global` likewise now also styles the banner inside an Angular `<ap-banner class="ap-global">`.
- **`ng-package.json`** doesn't list the library's styles as assets yet, so a published package wouldn't include them. The app builds from source, so this doesn't matter until the library is published.
