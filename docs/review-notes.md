# Review notes

Decisions made and findings noted while building the milestones without review, for the team to confirm, change or move into the other documents. Each says what was done, why, and what would change it.

## Deviations from engineering.md

Confirmed by the team on 2026-11-03: the hand-written API client, reflection-based JSON for the admin API, and every replica voting.

- **The admin API uses reflection-based JSON**, not source generation. Mediator maps the actions and serializes their results itself. The replicated state and the access logs use source generation.
- **The UI's API client is written by hand** (`src/web/projects/apiary/src/app/api/api.ts`), not generated from the OpenAPI document. Every action is a `POST /api/<area>/<action>` with a JSON body, so a generator would add little for now. Revisit when the API stabilizes.
- **Component styles are global**, in `@datapoint/apiary-ui`'s `apiary.css`, as the design system ships them, instead of per-component styles. Moving them into components would split the design system's single stylesheet.
- **Expected failures in handlers throw `ActionFailedException`** with an error code and a kind (not found, conflict, unavailable, forbidden, throttled, invalid), mapped to ProblemDetails in one place. Field-specific failures throw FluentValidation's `ValidationException` instead, so they reach the right field.
- **Mediator action names are lowercase with hyphens** (`users.change-role`), because Mediator only accepts those.
- **Apiary has its own small ACME client** (RFC 8555, in `Datapoint.Apiary.Certificates/Acme`) instead of a library. The usual .NET library, Certes, brings BouncyCastle and isn't maintained much; ours is about 300 lines on `HttpClient` and `ECDsa`, behind `IAcmeClient`. Like the join protocol, it's security-relevant code to review.
- **ASP.NET Core Data Protection is registered** by `AddAuthentication()`, though Apiary doesn't use it. Its key ring is kept in memory, unencrypted (`InMemoryKeyRing`), so nothing reaches the disk and no warnings are logged.

## Product decisions

- **Route timeout:** 1 to 120 seconds, 30 by default.
- **Loopback is in the default admin allowlist**, besides the private ranges, so `docker compose` with the admin port bound to `127.0.0.1` works, and so does `apiary users create-admin` from inside the container.
- **Password minimum is 15 characters**, as architecture.md says. The prototype said 12.
- **Sessions last 12 hours, and end after 15 minutes without activity** by default (`users.session-policy`, `users.update-session-policy`, from 5 to 720 minutes, on the Users page). They live in the replicated state, so signing out or disabling a user ends them on every replica. Signing in therefore needs a majority of voters; reads with an existing session don't. Writing every request's time to the state would cost a Raft write per click, so the last activity lives in a second cookie instead (`apiary_activity`, sealed with a key derived from the root key and bound to the session), renewed at most once a minute. Without it, the session's start counts as the last activity, so deleting the cookie doesn't help. The UI marks its requests as background (`X-Apiary-Background`) when nobody has used the page for a minute, so pages left open still sign out. That header is trusted, which is fine for its purpose: the timeout protects unattended browsers, not stolen cookies. Agents aren't affected.
- **Signing in has two steps.** The password step changes nothing; the code step starts the session. A short-lived challenge, encrypted with AES-GCM, carries the account between them.
- **Failed sign-ins are throttled per account and IP address**, in memory: free for 3 tries, then 2, 4, 8 seconds and so on, up to 15 minutes. The 5th failure in a row is audited.
- **Requests from other sites to the admin API are refused** using `Sec-Fetch-Site` and `Origin`, besides the `SameSite=Strict` cookie. Same-site requests are refused too, since apps routed by Apiary on sibling subdomains are same-site.
- **`apiary users create-admin` needs `--email` as well as `--name`**, since the email is the sign-in name. It reaches the running server with a token that Apiary writes to `{data}/operator-token`, readable only by its own user, and accepts only over loopback.
- **Users list:** Administrators only, since it lists everyone's email. The audit log stays readable by every role, as architecture.md says.

- **The root key is text, `apiary-root-key-1:` and 32 random bytes in base64url**, so a wrong file (e.g. a password) is refused instead of being used as a key. Keys are derived from it with HKDF-SHA256, one purpose string each.
- **State at rest:** `state/keys.json` holds the data keys, wrapped with AES-GCM by a key derived from the root key. Every log entry and the snapshot are encrypted with the current data key (AES-GCM, with a purpose string as associated data). **The leader adds a new data key every 90 days** (`Apiary:DataKeyLifetime`) in a replicated entry, which every replica adds to its key ring as it applies it; later entries use the new key. Old keys stay in the ring, since older log entries and snapshots still need them, so rotation limits how much each key encrypts rather than retiring keys. The new key travels in the Raft log, encrypted with the previous data key at rest and by TLS between replicas.
- **The generated root key lives in `/keys`**, a separate volume from `/data`, in the image and the Compose file.

- **Automatic certificates renew when a third of their lifetime is left** (30 days for today's 90-day certificates), so shorter Let's Encrypt lifetimes need no change. After a failure Apiary retries in 5 minutes, 15 minutes, 1 hour, then every 6 hours. [ACME Renewal Information](https://datatracker.ietf.org/doc/rfc9773/) isn't used yet.
- **Certificate keys are ECDSA P-256**, and so is the ACME account key.
- **An automatic certificate no route uses is kept for 30 days**, then deleted, so re-adding a route doesn't hit rate limits.
- **HTTP is redirected to HTTPS (308) only once a hostname has a certificate.** Until then the route answers over HTTP, so the first certificate can be requested. HSTS is a per-route choice, off by default (`strictTransport`, with `strictTransportSubdomains`), sent for a year on HTTPS responses only. It covers the whole hostname on every port, whichever route of that hostname answers.
- **`PublicHttpsPort` (443)** is the port used in redirects and in the `alt-svc` header for HTTP/3, since the container listens on 8443 and the port is published as 443. Kestrel's own `alt-svc` header is off, because it would advertise 8443.
- **A TLS connection for a hostname with no certificate is refused** during the handshake. There's no default certificate, so clients without SNI get no HTTPS.
- **Uploaded certificates:** RSA or ECDSA keys without a passphrase, at most 64 KB of PEM each. The chain must reach a root, either publicly trusted or included in the upload, so internal CAs must include their root. The check step shows what the certificate covers before it's added. Each belongs to a project, like routes.
- **The upload dialog's fields take a dropped file**, a chosen file or pasted PEM. A dropped file is read in the browser and goes in the field, like a chosen one.
- **"Renew now" waits for the result** in the request, which takes a few seconds against Let's Encrypt.

- **Every replica votes.** architecture.md describes voters and non-voting followers with a voter count, but DotNext.Net.Cluster has no non-voting members, so milestone 4 makes every replica a voter. Run 3 or 5 replicas: 3 tolerate one down, 5 tolerate two, and an even count adds no tolerance. Followers would need either a DotNext change or our own state shipping to non-members; decide whether they're worth it before milestone 5's voter replacement.
- **A replica reports healthy while it joins, in Swarm.** architecture.md says the health check passes once a replica has caught up. But `tasks.<service>` lists only healthy tasks, so a replica that waited for its health check before joining could never be found. In Swarm the check passes from start until the replica has joined and caught up, then reflects readiness. So a rolling update may stop the next replica before this one has caught up. To keep the majority, a stopping replica waits up to 15 seconds for every other task in `tasks.<service>` to be ready before it leaves (within the 30-second `stop_grace_period`), and a stopping leader hands over before leaving, resigning again if it wins the next election itself. Watch this with large states, which take longer than 15 seconds to catch up.
- **Membership is by address.** DotNext identifies members by IP address and port, and a Swarm task gets a new address on every restart. A restarted replica announces itself to the leader, which swaps its old address for the new one using the replica's ID (or its node). On a full restart, each replica rewrites its member list from what peers report, using the state and a local history of which replica had which address (`raft/addresses.json`).
- **If replicas restart while there's no majority, the cluster may not re-form on its own.** Each one's member list can then hold addresses the others no longer use. Restarting the whole service fixes it (`docker service scale apiary=0`, then back), which the replicas log as a hint. A replica learns its peers' new addresses from their answers while it starts; it now waits, up to 20 seconds, until every member it knows has answered with an address, and a replica answers only once it knows its own. Before that, two full restarts in three left the cluster without a majority; after it, six in a row re-formed in about 12 seconds. A replica that starts more than 20 seconds before the others still keeps their old addresses; if it isn't ready after 45 seconds and a peer answers from an address its member list lacks, it restarts, which Swarm turns into a fresh start that learns every address and announces itself to the leader. A ready replica never restarts this way; it only logs the hint. Tried by starting slot 1 30 seconds early: it restarted once and every replica was ready after 73 seconds. Tried with two replicas cut off and a rolling update; forced recovery covers what this doesn't.
- **Slot 1 creates the cluster.** It does so only when every peer it can see answers that there's no cluster. If slot 1's volume is lost while the other replicas are down, slot 1 starts a new, empty cluster; the others then refuse to join it ("another Apiary cluster answers") and stop, so it fails loudly rather than mixing states. Recovering means removing slot 1's new volume. Milestone 5's recovery should cover it.
- **Writes during a leader change** wait up to 15 seconds for a leader (in practice 2 to 3 seconds when the leader's node stops). With no leader known for 3 seconds, Apiary answers `cluster.noQuorum` (503) instead of waiting longer.
- **Read your writes.** After a command forwarded to the leader, the follower waits until it has applied the leader's index before answering. A request whose session cookie a follower doesn't know yet makes it check with the leader first (a read barrier, at most 2 seconds), so a session works on every replica right after signing in.
- **The replicas page shows the leader's view.** Followers don't talk to each other in Raft, so a follower asks the leader which replicas it can reach. Without a leader, it shows its own view.
- **Membership mode is a cluster setting**, on the Replicas page (`cluster.update-membership`), automatic by default, so a new cluster always forms on its own. In manual mode a replica Apiary hasn't seen before asks to join and waits; the replicas it asks keep it in memory for a minute after its last try, and the page shows the leader's list. Approving writes its ID to the state, and its next try (every 2 seconds) joins. A replica that leaves cleanly, as in a rolling update or a scale-down, keeps its approval, so updates need no approvals; one removed while missing, or whose volume is new, needs approval again.
- **Missing replicas are removed after 5 to 1440 minutes** in automatic mode (the prototype's range); never in manual mode, where an administrator uses "Remove now". "Remove now" only works on unreachable replicas.
- **A replica that isn't ready answers 503** on the public and admin ports (`cluster.notReady`, and a "starting" page for sites), instead of serving an empty configuration while it joins or waits for approval. The health check still passes in Swarm, as above.
- **A replica removed while it was unreachable restarts** when it comes back and sees that the others have a leader without it, then joins again as a new replica (or waits for approval). Before, it kept serving its last configuration with no leader.
- **The cluster CA rotates in three steps, a day apart** (`Apiary:ClusterCaOverlap`), starting 180 days before it expires (`Apiary:ClusterCaRenewBefore`; it lasts 2 years): the leader adds the next CA, which every replica then trusts; then replicas switch to certificates from it; then the old CA is dropped. Each step is a replicated entry, and each replica swaps its credentials as it applies it, without restarting. A replica that was away for a whole step catches up when it restarts, since joining hands it the current CAs.
- **Replica certificates are renewed 30 days before they expire** (they last 90 days). Before, a replica got its certificate only when it started, so one running for 90 days would have been refused by its peers.
- **Backups are files the administrator downloads**, not copies kept by the cluster. They're sealed with a key derived from the root key (`apiary/backups/1`), so they're as safe as the root key, and a backup can't be opened after the root key is rotated unless the old key is kept. Restoring signs everyone out. Restore is also offered on the setup page, so a lost cluster can be rebuilt from a backup without an administrator.
- **Forced recovery** (`apiary recover --force`, run inside a container) makes that replica the only member of a new cluster, with a new cluster ID and a new cluster CA, and signs everyone out. It refuses while there's a majority, and when a reachable replica has more changes. The old replicas then find the new cluster (every 15 seconds each replica asks the peers outside its member list), move their state to `/data/superseded-<time>/` and rejoin as new replicas. Tried with two of three replicas paused. **Risk:** if the old replicas come back as a majority, they keep accepting writes until they notice the new cluster, at most about 15 seconds; those writes are lost. The archived state is kept, so nothing is deleted, but it isn't merged back either. Clean up the `superseded-*` directories by hand.
- **The recovery wizard** on the Replicas page (Danger zone, Swarm only, Administrators) does the same from the admin interface. A cluster without a majority can't write, so it can't sign anyone in or run commands; the wizard uses two endpoints the replica handles on its own (`/api/cluster/recovery-plan` and `/api/cluster/recover`), open only to Administrators who are already signed in. The CLI stays for when nobody is. It asks for the replica's name, the password and an authenticator code, with the sign-in throttle. Recovery codes aren't accepted, since using one needs a write; for the same reason, the code isn't marked as used, so it could be replayed within its 30-second window by someone who also has the password and the session. The request carries the name typed, and a replica refuses one meant for another (`cluster.otherReplica`): through Swarm's ingress, the check and the request can reach different replicas. A browser usually keeps one connection, so both reach the same replica; when they don't, nothing changes and the person starts again. The plan lists the unreachable voters as the replica that answers sees them. The audit entry names the Administrator and their address. Tried in Swarm with three of four replicas paused (wrong password, wrong code, a request for another replica, then recovery; the other replicas rejoined) and in the browser with three replicas cut off the cluster network.
- **Replies over 16 KB aren't remembered for retries** (`AppliedRequests`), e.g. a backup export. Retrying such a command runs it again; the ones affected are reads, so it's harmless today.
- **No automatic certificates for `localhost` and `*.localhost`.** Let's Encrypt can't issue them ([RFC 6761](https://datatracker.ietf.org/doc/html/rfc6761)), so asking only filled the logs and the audit log with failures. `.test` hostnames still get them, since Pebble serves them.

- **The root key rotates in one deploy**: create a second secret, point the stack at it and redeploy, as architecture.md describes. A replica whose state the new key can't open uses the certificate it saved on its volume to fetch the data keys from a peer, wraps them with the new key and rejoins. The state records which root key each replica uses (an ID derived from the key, shown on the Root key page and by `keys.status`); join messages carry that ID, so replicas on the old and new keys verify each other during the update. Once every replica reports the same key, the leader forgets the older ones on its own; the prototype had a "Forget old key" button instead, which isn't needed. Rotation needs at least 2 replicas, since a single replica has no peer to fetch the keys from: it keeps asking, so mount the previous key again to bring it back. Tried with 3 replicas, then a 4th added on the new key.
- **Route status shows Active, Disabled or In maintenance.** The prototype's "Healthy" and its "Needs attention" filter need health checks, which come later; the list has an All/Disabled filter for now. Row actions are icon buttons (enable or disable, delete) rather than the prototype's menu, since the component library has no menu yet.
- **Allowed addresses are checked against the connection's own address**, never `X-Forwarded-For`, at most 100 entries per route. **This only works with host-mode ports**, as in `deploy/stack.yaml`: Swarm's ingress routing mesh replaces the client's address with its own, so every visitor would look like `10.0.0.x`. Say so in the deployment docs, and consider refusing or warning about allowlists when Apiary can tell it runs behind the mesh.
- **Maintenance windows:** one per route, up to 7 days, ending in the future (the start may already have passed, so an ongoing window can be edited). Times are UTC in the UI, like the rest of Apiary. The visitor message is plain text, HTML-encoded, at most 200 characters, and the 503 carries `Retry-After` for the time left. The prototype's "health checks pause" has nothing to pause yet.
- **Redirects belong to a project** (architecture.md), so the add dialog has a Project field the prototype lacks. The API accepts 301, 302, 307 and 308; the dialog offers 308 and 307, as in the prototype. A redirect has no edit action, also as in the prototype: delete and add it again. Once its automatic certificate exists, an HTTP request takes two hops (to HTTPS on the same hostname, then to the target), which keeps HSTS-style upgrades consistent. The Certificates page doesn't yet show that a redirect uses a certificate.
- **Deleting a project moves what it holds in the same change.** architecture.md says a project is deleted only once it's empty. `projects.delete` takes an optional `moveTo`, and moves the project's routes, redirects and uploaded certificates there in the same state change before deleting it, as the prototype's "Move routes and delete" does; without `moveTo`, a project that isn't empty is refused (`project.notEmpty`). So nothing is ever left without a project, and there's no half-moved state. The last project can't be deleted (`project.last`): routes and redirects need one.
- **Project names are unique regardless of case**, at most 40 characters, with a description of at most 120, as in the prototype. Project URLs use the id, not a slug made from the name, so renaming never breaks a link.
- **Milestone 7 leaves out what needs metrics or health checks**: the overview's request, latency and error cards, its time range, project health on the cards, and requests per minute; milestone 8 adds them. The sidebar has an "All projects" link rather than the prototype's "New project" button (the button is on the Projects page), and the project page's actions are icon buttons rather than a menu.
- **Deleting several routes sends one `routes.delete` per route**, so the audit log has one entry each and a failure part-way leaves the rest. The prototype's "Purge cache" bulk action waits for caching.
- **The overview shows a "Get started" checklist** to Administrators while there are no routes: the administrator (done), a project besides Default, the first route and a second person, with a reminder to take a backup. It goes away with the first route, whoever adds it.
- **The audit log's filters**: a range (24 hours, 7 days, 30 days, a year, or a custom range in UTC within the year kept), a person, failed only, through people, agents or the system, and text found in the action, the user, the agent, the address or the affected names, ignoring case. The page shows the newest 500 entries that match.
- **Target health checks have no settings.** The prototype's route editor has none, so every target gets `GET /` every 15 seconds from every replica, with a 5-second timeout; with 3 replicas that's 12 requests a minute per target, which shows up in the targets' own logs. Any HTTP answer counts as up, because a stricter check (2xx only) would take a site that answers 401 or 404 at `/` out of rotation. If a team needs a real readiness check, add an optional health path per route.
- **Route health and requests per minute come from every replica**, over the replicas' mutual TLS, and are cached for 5 seconds. A target counts as down only if no replica reaches it; a replica that can't be reached isn't counted, so requests per minute dip while one is missing. Which replicas are reachable comes from the leader, since a follower only hears from the leader; until 2026-11-03 each follower counted only itself and the leader. A replica that doesn't answer is logged as a warning. Rates cover the last 50 to 60 seconds, so they're approximate.
- **`/metrics` needs no sign-in**, like `/health`: Prometheus scrapers don't sign in. It's on the admin port, behind its allowlist, and shows hostnames and route ids, not personal data. Turn it off with `Apiary__Telemetry__Prometheus=false` and use OTLP instead if that's too open.
- **The Prometheus exporter is a prerelease package** (`OpenTelemetry.Exporter.Prometheus.AspNetCore` 1.20.1-beta.1): OpenTelemetry has kept it in beta for years while the rest is stable. It's pinned, and OTLP export doesn't depend on it.
- **Milestone 8 leaves out** access logs over OTLP (architecture.md calls it optional).
- **The overview's request, latency and 5xx cards** (`activity.get`) cover the last hour, in 1-minute points, or the last 24 hours, in 15-minute points. Each replica keeps a 24-hour ring of per-minute counts in memory, with a histogram of response times; the replica that answers asks the others for the same minutes (`/cluster/activity`) and adds them up, cached for 10 seconds. p95 comes from the summed histogram, since percentiles can't be averaged across replicas, so it's an estimate within its bucket (for example, 15-second responses show as about 20 seconds). A restart clears that replica's share, and a replica that can't be reached isn't counted, so the cards are a glance, not a record; long-term history belongs in a monitoring system fed by `/metrics` or OTLP. A request the client abandons is counted with the status it had, usually 200, as in the access log.
- **Agents (milestone 9).** Codes last 2 minutes and work once, access tokens 1 hour, refresh tokens 30 days and rotate on every use, and a connection ends 90 days after it was approved, whatever its tokens, so a stolen refresh token that keeps being used doesn't last forever. The Connected agents page shows when; reusing an earlier refresh token, however old, or a code already exchanged disconnects the agent, as OAuth 2.1 recommends, with an audit entry under its user, since it usually means a token was stolen. Refresh tokens are sealed with the agent's id, so Apiary can tell an earlier token from a made-up one, and nobody can disconnect someone else's agent by guessing. If a refresh answer is lost on the way, the agent has to be connected again. Connecting the same client again (same client id) replaces its earlier connection, and a user can have at most 20 agents. Administrators see and can disconnect everyone's agents; others see their own. The prototype's "Calls, 30 days" column isn't built: Apiary doesn't count calls, so the page shows when the agent last got a token ("Last active", within the hour while it works). The prototype's "Connect an agent" dialog is a panel on the page instead, with the `claude mcp add` command. Disconnecting needs no typed confirmation.
- **Agents get every action except** `certificates.upload` and `certificates.check` (they take private keys), `backups.export` and `backups.restore` (the whole state), and the actions only a person should take: `auth.*`, `account.*`, `setup.*`, `invites.*`, `oauth.*`, and approving agents (`agents.connect`, `agents.client`). So an agent can't change its user's password or two-step sign-in, or connect other agents. The list is in `Datapoint.Apiary/Agents/McpSetup.cs`.
- **The MCP transport is stateless**, so any replica answers any request and nothing breaks on a leadership change or a rolling update. It means no server-to-client notifications, which Apiary's tools don't need.
- **Client registrations aren't stored.** Dynamic client registration is open to anyone who reaches the admin port (the MCP specification expects it), so the client's name and return addresses are sealed into its client id with a key derived from the root key, and nothing is written until a user approves. A root key rotation makes ids of clients that never connected invalid; connected agents keep working, since their refresh requests are checked against the stored id. Return addresses must be HTTPS, or HTTP on the loopback address.
- **Token requests aren't audited**, since an agent refreshes every hour. Connecting, disconnecting and revoking are. Changes an agent makes are recorded under its user, with the agent's name as the client.
- **Releasing new versions (milestone 10) follows the prototype.** Each target is its own group (a Swarm service is already a group of tasks), with a weight; weights add up to 100 with two or more targets, and a route has at most 10. The canary header or cookie always sends requests to the last target, matching its value exactly, and the canary target also gets its weighted share of other traffic. Sticky sessions are a switch: the cookie's name (`apiary_affinity`) and lifetime (1 hour) are fixed, where architecture.md had them set per route. If a team needs other names or lifetimes, add the fields.
- **`routes.update` replaces every setting**, including the new ones, so an agent or script that leaves out `canary`, `sticky`, `compression` or `caching` turns them off. The tool description says so. A partial update action would be friendlier for agents.
- **Caching details.** Each replica has up to 256 MB of cache, and stores responses of at most 8 MB, for at most a day. Only `max-age` and `s-maxage` count; `Expires`, `stale-while-revalidate` and validation with `ETag` aren't used. Responses that vary by anything other than `Accept-Encoding` aren't stored. Responses that set cookies are never stored, even when `public`, which is stricter than architecture.md said: storing one would hand one visitor's cookie to the next. Purging is recorded in the route, so a replica that's cut off keeps serving its cache until it catches up.
- **Compression uses the fastest level** of Brotli and gzip, to spend little CPU per request, and adds SVG to ASP.NET Core's default types.
- **Single sign-on (milestone 11) is one OpenID Connect provider**, set on the Single sign-on page (`sso.get`, `sso.update`, Administrators only, withheld from agents). Apiary uses the authorization code flow with PKCE (S256), a nonce and a state, kept in a sealed cookie (`apiary_sso`, 10 minutes, SameSite Lax, path `/auth/sso`), and authenticates to the provider with `client_secret_basic`. It reads the provider's configuration and keys from `/.well-known/openid-configuration` with `Microsoft.IdentityModel.Protocols.OpenIdConnect` (a new package, from Microsoft), and accepts only RSA, RSA-PSS and ECDSA signatures. The redirect URI is `/auth/sso/callback` on the address people open Apiary at, shown on the page with a copy button. Issuers must be HTTPS; `Apiary__AllowHttpSsoIssuer=true` allows HTTP, for trying it with a local provider only.
- **Roles come from groups at every sign-in.** Someone in several mapped groups gets the highest role, someone in none can't sign in (`sso.noRole`, audited as a failed sign-in). The groups claim is configurable (`groups` by default) and may be a list or a single string. Entra ID sends group ids rather than names unless configured otherwise, and leaves the claim out for people in more than 200 groups ("groups overage"), which Apiary doesn't follow up with Microsoft Graph: those people can't sign in. Apiary asks for the `openid email profile` scopes and needs the `email` claim; an `email_verified` of false is refused.
- **Accounts from the provider are separate from password accounts.** A user is found by issuer and subject (`User.ExternalId`), never by email: if a password account already has the email, sign-in is refused (`sso.emailTaken`), since linking by email would let whoever controls the provider take over that account. Name, email and role are copied from the provider at every sign-in, so in Apiary their profile is read-only and their role can't be changed (`user.managedBySso`). They have no password and no Apiary two-step sign-in: the provider is trusted to require MFA. Disabling or deleting them in Apiary works as for anyone; disabled users are refused. Turning single sign-on off or changing the issuer ends their sessions, and since the issuer is part of their identity, users from an old issuer must be deleted before people can sign in from a new one with the same email.
- **The provider can demote the last Administrator.** architecture.md says Apiary refuses to demote the last Administrator, but roles from groups follow the provider. The page asks to keep a password Administrator as break-glass, as architecture.md plans; Apiary doesn't enforce it. Decide whether saving settings should require one.
- **After the callback, Apiary answers with a small page that moves on to the app** instead of a redirect, so the browser sends the new SameSite Strict session cookie on the next request. Only relative paths are allowed as the destination. Errors send the browser back to the sign-in page with a code (`/sign-in?error=sso.failed`), which the page explains; details go to the log, never to the browser.
- **The validated identity reaches the leader sealed.** The replica that handles the callback checks the ID token, then sends `auth.sso` with the identity sealed by a key derived from the root key (valid 2 minutes), because commands are forwarded to the leader by action name and the leader has to trust them. `auth.sso` is anonymous on `/api`, so anyone can call it, but only with a sealed identity, which never leaves the replicas.
- **Stream routes (milestone 12) can use any port** except Apiary's own (8080, 8443, 9443, 9444, 9445), rather than a fixed range as architecture.md suggested; the prototype lets people pick ports such as 1883 or 514. Apiary can't see which ports the stack file publishes, so the page and the add dialog say to publish the port and show the line to add. Ports below 1024 work because Docker lets containers bind them without root by default. If a port can't be bound (another process has it), the replica logs an error and tries again every 30 seconds; the page doesn't show it yet.
- **TLS passthrough reads the first TLS record only** (up to 16 KB, within 10 seconds), takes the server name from it, and passes the bytes on unchanged. Names match exactly first, then wildcards (`*.example.com` matches one label, not `a.b.example.com`), then the port's route without names, if any; otherwise the connection is closed. Two TCP routes on one port can't share a name, and only one can have none. Encrypted ClientHello (ECH) hides the real name, so clients that use it reach the fallback route.
- **Stream route limits:** per port on each replica, 10,000 TCP connections (counting ones still waiting for their first bytes or their target) and 256 from one address, or 1,000 UDP sessions and 64 from one address. Each UDP session holds a 64 KB receive buffer, so 1,000 sessions use about 64 MB; UDP source addresses can be forged, so the per-address limit doesn't stop a flood from many forged addresses, only the total does. A 10-second connect timeout, UDP datagrams up to 65,527 bytes, idle timeouts from 1 to 3,600 seconds (60 by default). TCP connections have no idle timeout; they last until either side closes, and a half-close (one side done sending) is passed on. Changing a route's target, port or protocol, or deleting it, closes its open connections; renaming it doesn't. The target's address is resolved for each new connection or session, through the same checks as HTTP targets (no loopback, link-local or Apiary itself).
- **Stream routes have allowed addresses and a disable switch**, like HTTP routes. A connection or UDP client from anywhere else is closed at once, without reaching the target, and narrowing the list closes open connections it no longer allows. A disabled stream route frees its port on every replica, but the port stays reserved for it. Like HTTP routes, the allowlist needs host-mode ports, since Swarm's ingress hides the client's address. They still have no health checks. The Status column shows "Active" while connections are open or one opened in the last hour, otherwise when the last one opened, or "No connections yet": the latest across replicas, kept in memory, so a restart forgets it.
- **Fixed: restoring a backup on a running cluster kept the current redirects** instead of the backup's.
- **Form checks that need the server** are read-only queries (`routes.check`, `redirects.check`, `projects.check`, `streams.check`, `users.check-email`), sent 400 ms after typing stops, while the field shows "Checking…". They return the same codes as the validators, from the replica that answers, which may be a moment behind the leader; saving checks again on the leader. They aren't offered to agents, whose saves report the same errors.
- **State changes carry a schema version, for rolling upgrades.** A replica on an older version can't read a change type it doesn't know, and fails to replicate, so a leader on a newer version could break the majority mid-update (found while trying the CA rotation). Replicas now report the schema they understand when they join, and the leader refuses an entry that needs a newer schema than every replica has (`cluster.upgrading`, 503) until the update finishes. Everything is schema 1 for now. **Proposed rule for engineering.md:** after 1.0, a new `IStateChange` type bumps `StateSchema.Current` and gets `[StateSchema(n)]`; changing an existing type's JSON in a way older versions can't read counts as new.
- **Password-protected routes don't bump the state schema.** `Route` gained a `Password` property, which an older replica would ignore and so serve the route without asking for it. The schema rule above applies from 1.0, and nothing runs mixed versions yet, so it stays schema 1; after 1.0, a change like this needs `[StateSchema(n)]`.
- **The password cookie's signing key is per route, in the replicated state**, rather than derived from the root key, so it works on every replica during a root key rotation and a new password signs everyone out without a version counter. It's as protected as the password hash next to it: encrypted at rest, never returned by the API.
- **The password page answers 401 without `WWW-Authenticate`**, since it's a form, not HTTP authentication; too many tries answer 429 with `Retry-After: 300`. A POST from the site's own forms while signed out gets the password page; Apiary only reads a form marked as its own (`apiary-gate`), up to 4 KB.
- **A new password keeps the sign-in link**, and a new link keeps the password, as in the prototype; each is replaced on its own.
- **Which brand a page uses** follows the prototype: maintenance, password and sign-in link pages use the route's project brand, the 403, 429 and disabled pages the cluster's, like the 404. The "Starting" page has no brand, since the state may not be loaded yet.
- **Brand actions are for the admin UI only** (`brands.list`, `brands.save`, `brands.remove`, not on MCP), since they carry logos of up to 100 KB.
- **Not built from the prototype: previews of each visitor page** from the Visitor pages screen. The brand dialog's live preview of the password page is built.
- **The interface language uses runtime catalogs** keyed by the English text, not Angular's built-in i18n, which would build the app once per language and reload to switch (decided with the team on 2026-11-04). The choice is saved in the user's profile (`account.set-language`, en or pt-PT); `auth.me` returns it. It doesn't bump the state schema either. Before sign-in and on visitor pages, the browser's language decides.
- **Visitor pages pick their language per request**, so they send `Vary: Accept-Language`; a cache in front of Apiary keeps one copy per language.
- **Not translated:** MCP descriptions for agents (English, as engineering.md says), the server's log messages and ProblemDetails `title`s, and anything an operator types, such as a maintenance message or a visitor page's contact line.

## Security findings to resolve before 1.0

- **Fixed: recovery codes had about 40 bits of entropy**, few enough to find offline from their SHA-256 hashes by someone holding both the state and the root key. New codes have 16 characters in 4 groups, about 79 bits; codes issued before still work until they're used or replaced.
- **Accepted: the state log isn't bound to its order.** Each entry is encrypted and authenticated on its own, so someone who can write to the state volume can't forge or change entries, but could drop the last ones or replay a copy of the volume from earlier. Binding entries to their index or to the previous entry isn't possible safely: DotNext assigns the index after Apiary encrypts the entry, and guessing it would stop a replica from applying the log whenever a new leader adds its own entry. A chain wouldn't stop either attack anyway, since an older copy of the volume is consistent with itself. Raft covers it with 3 or more replicas; the rest is documented in [risks.md](risks.md) and rated low.
- **Fixed: Apiary generated a root key whenever none was mounted.** In Swarm it now refuses to start without the secret, as architecture.md says.
- **Fixed: the common-password list was short.** Apiary now embeds 124,430 passwords of 15 characters or more from [SecLists](https://github.com/danielmiessler/SecLists) (MIT), from its 10-million list and the NCSC's 100,000 most used, compared regardless of case, on top of the checks for repeated characters and keyboard or alphabet runs. `Apiary__CheckBreachedPasswords=true` also checks new passwords against Have I Been Pwned's range API, with padding; if the service can't be reached, the password is accepted and a warning logged.
- **Fixed: the admin port was plain HTTP.** It's now HTTPS from the first start, so the session cookie is marked `Secure`. The leader creates a self-signed ECDSA certificate for `localhost` (2 years, renewed 30 days before it expires) in the replicated state, so every replica serves the same one, and each replica logs its SHA-256 fingerprint at start and next to the setup address. Administrators can upload their own on the Certificates page, with the same checks as other uploads, or go back to a self-signed one (`admin-certificate.get`, `admin-certificate.upload`, `admin-certificate.reset`; upload is withheld from agents). Until the state has one, a replica serves a temporary certificate, behind the readiness gate. The CLI commands (`health`, `users create-admin`, `recover`) talk to `https://127.0.0.1` and accept any certificate there, since anyone who can intercept loopback already runs in the container. Uploaded certificates still need a DNS name: one with only IP addresses is refused.
- **Fixed: backups, recovery and private keys stay off MCP** (`backups.export`, `backups.restore`, `setup.restore`, `certificates.check`, `certificates.upload`), as milestone 5 asked.
- **Fixed: other sites could frame the admin interface** (clickjacking). It now sends `X-Frame-Options: DENY` and `frame-ancestors 'none'`. That mattered more once the agent consent page existed.
- **Fixed: no Content Security Policy.** The admin port now sends `script-src 'self'`, with `style-src 'self' 'unsafe-inline'` because Angular and the design system set inline styles, plus `object-src 'none'`, `base-uri 'self'` (for Angular's `<base href>`) and `form-action 'self'`. Angular's critical-CSS inlining added an inline script, so it's off; the UI loads its stylesheet normally. Apiary's own public pages (404, starting, disabled, maintenance) send `default-src 'none'` with inline styles only. The admin port also sends HSTS for a year, but only with an uploaded certificate and when it's opened by a hostname other than `localhost`: browsers ignore it for IP addresses, and with a self-signed certificate it would stop people from accepting it. Switching back to a self-signed certificate after that makes browsers that kept HSTS refuse the admin interface until it expires.
- **Fixed: anyone on the internal network could register an MCP client that returns to a site of their own**, under any name such as "Claude Code", and send an Administrator a link to approve it, gaining their access. Agents now return only to the user's own computer (`localhost` or a loopback address, over HTTP or HTTPS), or to HTTPS origins an Administrator lists on the Connected agents page (`agents.policy`, `agents.update-policy`, at most 20, empty by default, withheld from agents). The rule is checked when a client registers, when the consent page opens and when the agent is approved; removing an origin disconnects the agents that return there. Registration refused for this answers `invalid_redirect_uri` with a description, so whoever sets up a web-based agent knows what to ask for. The consent page still warns when an agent returns to a website.
- **Agents stay connected when their user changes their password** or two-step sign-in. Decided on 2026-11-03: they stay connected. They stop when the user is disabled or deleted, when the cluster is restored or recovered, or when someone disconnects them.
- **The `resource` parameter (RFC 8707) isn't checked.** Apiary's tokens work only on its own MCP endpoint, so there's no other audience to confuse.
- **MCP clients must trust the admin certificate.** The MCP endpoint and OAuth now run over HTTPS like the rest. With the self-signed certificate, clients that verify certificates (most do) refuse to connect until the certificate is trusted on that computer or replaced by one from a CA it trusts.
- **The leader trusts the user a follower forwards.** A forwarded command carries the user's claims. For a session or an agent the leader rebuilds the user from the state, but other sign-in types (the local operator token) are taken as sent. Any replica can already read the whole state with the root key, so this adds little, but it's worth knowing when reviewing the cluster port.
- **The join endpoint accepts anonymous TLS** on the cluster port (9445, on the overlay network only). It's authenticated by an HMAC from the root key, with a time window of ±5 minutes, the requester's address checked against the one it claims, and the data keys sealed in the answer. Everything else on that port needs a certificate from the cluster CA. It's security-relevant code to review.
- **The proxy drops Apiary's admin cookies** (`apiary_session`, `apiary_activity`, `apiary_sso`) from requests it forwards, and from `Set-Cookie` in responses. Browsers scope cookies by hostname, not port, so if a route serves the admin interface's hostname, its target would otherwise receive admin sessions, or could set one. Still give the admin interface a hostname that no route serves.
- **Removing a replica revokes its certificates.** The state records when each replica was removed (for 90 days, the certificates' lifetime), and the cluster port and Raft refuse that replica's certificates issued before then. Only `/view` still accepts them, so a replica removed while it was unreachable can find out and rejoin, with a new certificate. Forwarding commands, appending entries, telemetry and challenges need a current member; `/announce` and `/leave` accept a replica speaking for itself, or a current member relaying.
- **Unknown session cookies cost a round trip to the leader** on followers (the read barrier above). The admin port is limited to the allowlist, so only allowed networks can cause it; add a rate limit if that changes.
- **Private keys are plain in memory** on every replica, and encrypted only at rest. That's inherent to serving TLS.
- **Each replica keeps its cluster certificate and private key on its volume** (`raft/credentials.json`, mode 600, not encrypted, since the root key that would encrypt it is the one being replaced). That's what lets a replica fetch the data keys after a root key rotation. The cost: someone with a copy of a data volume and access to the overlay network can fetch the data keys from a running replica until the certificate expires (90 days, or when the replica is removed from the cluster), without the root key. Treat data volumes as secret, like the root key; an alternative is to keep the old root key mounted next to the new one during a rotation, which architecture.md doesn't plan.
- **The single sign-on settings make Apiary fetch URLs an Administrator chooses** (the issuer, and the token and key URLs its configuration lists), from inside the Swarm. That's server-side request forgery limited to Administrators, who can already route traffic anywhere. Responses are limited to 1 MB and 10 seconds.
- **The client secret is stored in the replicated state**, encrypted at rest like private keys, and in backups. It's never returned by the API.
- **"Renew now" audit entries don't record the IP address**, unlike other actions, because the issuer writes its own entries.

## Regulatory findings

- **AGPL section 13.** The UI's "Source" link, in the sidebar and on the sign-in pages, points to the tag of the running version on `https://github.com/datapoint-software/apiary`. Before release, that repository must be public and the tag must exist, holding the code that's deployed.
- **Personal data:** the audit log shows email and IP addresses to every role, as the architecture allows, and the audit page says so.

- **The sticky sessions cookie** (`apiary_affinity`, 1 hour, HttpOnly) is set on the visitors of the sites behind Apiary, not on admins. It only keeps a visitor on one version, so it should count as strictly necessary under the ePrivacy rules and need no consent, but the sites' cookie notices should list it. It holds a hash of the target, nothing about the visitor.

- **Let's Encrypt's Subscriber Agreement.** Apiary agrees to the ACME server's terms of service when it creates its account, on the operator's behalf. The README and the Certificates page say so, with a link to the agreement.

## Known issues

- **Fixed: a snapshot from an older version couldn't be saved again.** System.Text.Json source generation sets an `init` property that's missing from the JSON to null, ignoring its initializer, so a new list in the state was null after an upgrade. New state properties now use a backing field whose getter falls back to an empty value. Watch for this whenever the state gains a property.
- **An interrupted rolling update can leave the member lists out of step**, so the replicas crash-loop. Restarting the whole service (`docker service scale apiary=0`, then back) fixes it, as above.

- **During a root key rotation, replicas on different keys disagree on keys derived from the root key.** A sign-in started on a replica on the old key can fail its second step on a replica on the new key (try again), and a backup is sealed with the key of the replica that exported it. Both last only until the update finishes.
- **A replica waiting for approval in manual mode reports healthy**, like any replica that's joining, so the rolling-update wait above (15 seconds) can't tell it from one that will be ready soon. Approve new replicas before an update.

- **Commit `1068cf3` doesn't build on its own**: a staged file move (`PublicPages` into the proxy project) went into it by mistake, and the next commit completes it. It's pushed, so it wasn't rewritten; skip it when bisecting.
- **Fixed: Apiary couldn't start on macOS** after root key rotation added saved credentials, because macOS won't export a private key once it's attached to a certificate. Linux, where it runs in production, was unaffected.

- **Mediator's known issue (English messages in error responses) is fixed for HTTP** by stripping title and detail in `ProblemDetailsCodes`, and for MCP by returning every error as structured content with its code (`McpSetup`), including authorization failures and arguments that can't be read, since Mediator 4.0.0-beta.6.
- **Claude Code itself wasn't tried against the MCP endpoint**: its sign-in had expired in the environment milestone 9 was built in. The same flow was tried with a script acting as the client (registration, approval in the browser, code exchange with PKCE, MCP calls on every replica, refresh, reuse refused, disconnect). Try `claude mcp add --transport http apiary http://<admin host>:<port>/mcp`, then `/mcp` in Claude Code to sign in.
- **Fixed: the public pages' colors were hard-coded.** The 403, 404 and 503 pages now embed the design tokens, so they follow the design system, in light and dark mode.
- **Fixed: routes answered 404 after a restart** until the next change, because loading the state didn't signal the proxy. Found while trying milestone 3; it existed since milestone 1.
- **HTTP/3 isn't verified.** Kestrel listens on UDP 8443 and advertises it, but no HTTP/3 client was available to try it. Check with `curl --http3` against a real deployment.
- **Fixed: a certificate lock held by a stopped leader made the new leader loop.** It wrote a state change on every try, and each change woke the renewal check again, about 100 entries a second until the lock expired after 10 minutes. It now checks the lock before writing. The same could happen on a single node after a restart during an issuance.
- **The design system's `> .ap-icon` selectors missed the Angular `<ap-icon>` wrapper**, so banner and toast icons had the wrong colors. They now match both forms. `.ap-global` likewise now also styles the banner inside an Angular `<ap-banner class="ap-global">`.
- **`ng-package.json`** doesn't list the library's styles as assets yet, so a published package wouldn't include them. The app builds from source, so this doesn't matter until the library is published.
