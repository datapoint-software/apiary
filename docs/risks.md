# Risks and considerations

Known risks of Apiary's design, and the precautions they need. Read this before changing how Apiary stores state, handles secrets or is exposed to the network.

- **Private keys.** Certificate private keys and the ACME account key are secrets. They must be encrypted at rest on each replica's volume and in transit between replicas, and never committed or logged.
- **Raft traffic.** Replication traffic between replicas must be authenticated and encrypted (e.g. mutual TLS or an [encrypted overlay network](https://docs.docker.com/engine/network/drivers/overlay/#encrypt-traffic-on-an-overlay-network)). Otherwise anything on the network could read or inject state.
- **Root key.** Every Apiary task can read the root key, so anyone who takes over an edge node can decrypt the state and impersonate a replica. Keep edge nodes hardened, limit who can deploy services that use the secret, and rotate the root key after any suspected compromise. The files in `deploy/` mount the key readable only by Apiary's user (uid 1654) and run the container with no Linux capabilities and a read-only root filesystem, so that a flaw in Apiary or a library is harder to turn into more; keep those settings when adapting them.
- **State rolled back on a volume.** Each state entry and snapshot is encrypted and authenticated on its own, but not bound to its place in the log: Raft assigns an entry's index after Apiary encrypts it. Someone who can write to a replica's state volume, such as root on its node, can't read or forge entries without the root key, but could cut off the last ones or put back an older copy of the volume. That brings back an earlier state that really existed, such as a revoked user, an old password or a deleted route. With 3 or more replicas, a rolled-back replica catches up from the majority, so the attack needs most replicas' volumes at once; with 1 replica it works on its own. Restoring an old copy of a volume by mistake has the same effect. Run 3 or more replicas, limit who is root on the edge nodes, and prefer Apiary's backups to copies of the volume. Rated low: whoever can write to the volume can usually also run commands in the container and read the root key.
- **Own join protocol.** A brand-new replica proves it has the root key with a small protocol of our own (an HMAC challenge, like Swarm's join tokens). Like the OAuth server, it's security-critical: build it from standard primitives, test it, and have it reviewed before release.
- **Own OAuth implementation.** Apiary implements its own OAuth authorization server, which is security-critical code that is easy to get subtly wrong (e.g. redirect URI checks, PKCE, token expiry and revocation). Follow the specifications closely, test it against them, and have it reviewed by someone with OAuth experience before release.
- **Unsafe scale-downs.** Apiary can refuse to step down voters, but it can't stop Swarm from stopping tasks. Scaling a highly available cluster to 2 replicas, or removing most of the voters in one deploy, loses the Raft majority and stops all writes until replicas come back. Scale down by at most one voter at a time, and never below 3 unless you mean to give up high availability by going to 1.
- **Forced recovery.** A forced recovery can lose the last few changes, including revocations. Its safeguards sign everyone out, but admins must still review users and roles afterwards, and redo any recent route or certificate changes that are missing. Prefer restoring a recent backup when there is one.
- **Known issue: English text in Mediator's HTTP errors.** On the HTTP API the UI uses, Datapoint.Mediator 4.0.0-beta.3 sends English text in two places, against the rule that the UI receives only error codes ([engineering.md](engineering.md#errors-are-codes-not-messages)): a request body that can't be read returns a 400 with an English title and the exception's message, and 401 and 403 have English titles. It's an inconsistency more than a risk: none of this text includes the caller's input, though the parser's message can name internal .NET types. Apiary maps its own errors, including FluentValidation's, to codes; these stay until Datapoint.Mediator lets applications shape them. On MCP, the same English text is intended: agents read it to explain the problem and correct their calls.
- **Stale DNS records.** With plain DNS in front of the edge nodes, a node that stops running a replica still receives traffic from clients that resolved its address, and those requests fail. Keep TTLs short and update DNS when scaling down, or use a load balancer with health checks.
- **Swarm managers.** If the edge nodes are also Swarm managers, Swarm's own Raft follows the same majority rules: with 2 managers, losing one stops all deploys and service changes, including Apiary's. Run 3 or 5 managers.
- **On-demand backups.** There are no scheduled backups: if nobody exports a snapshot, losing a majority of voters for good loses the state, including every route and admin account. Take a snapshot before risky changes and on a regular routine. Snapshots contain private keys, so store them encrypted, with restricted access. A snapshot can only be restored with the root key it was made with, and Swarm never shows a secret again: keep every root key in a secret store, apart from the snapshots, for as long as snapshots made with it are kept.
- **Routes to internal addresses.** Routes can point at any host and port, so a route can expose internal services to the internet: Apiary's own admin and Raft ports, the Docker API, or cloud metadata endpoints (e.g. `169.254.169.254`). Apiary refuses these (see [architecture.md](architecture.md#routing)), but other internal services, such as a Docker daemon listening on TCP port 2375 or 2376, can't all be known in advance. Admins should treat every new route as a publication.
- **Single-instance modes.** With 1 replica there is no high availability: if the machine or its disk is lost, so is the state, unless a backup was exported. When Docker Compose generates the root key, it sits on the same machine as the state, so encryption at rest only protects a copy of the state volume on its own.
- **Docker API access.** Apiary must not be given access to the Docker API, which is equivalent to root on the host, or control of the whole cluster for a manager node.
- **Shared overlay network.** Every service on the `apiary` network can reach every other service on it, not only Apiary. Services that should be isolated from each other need separate networks.
- **Admin interface exposure.** The admin port, which serves the UI, its HTTP API and the MCP endpoint, is published on every interface of the edge nodes, because Swarm can't bind to one. Keep the network firewall and Apiary's allowlist in place, and don't widen the allowlist to public ranges. Host firewalls like `ufw` and `firewalld` don't protect it: Docker's iptables rules bypass them.
- **AI agents.** An agent can be manipulated by text it reads (prompt injection), such as a hostname, a header or an upstream error message chosen by an attacker, into calling tools its user didn't intend. Agents have the same permissions as their user, so an agent connected by an Administrator can do anything an Administrator can, including creating users. Confirmation before commands depends on the MCP client: users can turn it off, unattended agents have no one to ask, and Apiary can't tell whether it happened. Connect agents with an account that has only the role they need (e.g. a separate Viewer account), disconnect agents that are no longer used, and review the audit log for agent actions.
- **Private keys and agents.** Anything an agent sends or reads also reaches its model provider. Private keys must never be offered through MCP: keep the certificate upload action out of the MCP tools, and never return private keys from any action.
- **Audit log contents.** Audit entries hold usernames and IP addresses, which are personal data under the GDPR. They are kept for 1 year by default, signed off by the data protection officer on 2026-11-02. Deployments that change it should record why, and backups keep entries for as long as the backups themselves are kept.
- **Pre-release dependency.** Datapoint.Mediator is in beta, so its API may change between versions. We maintain it, so breaking changes can be planned with Apiary in mind, but pin the exact version and read its changelog before upgrading. A security fix in the library needs a release of both.
- **First-access setup.** Until the first Administrator is created, anyone who can reach the admin port can create it. With Docker Compose that includes other containers on the same host, since Docker networks use private addresses. Complete setup right after the first deploy, then check that the setup entry in the audit log shows your own IP address.
- **Local accounts.** Apiary owns password storage and brute-force protection for local accounts, and they must be removed by hand when people leave. With single sign-on in use, keep local accounts to a few break-glass ones, with strong passwords stored somewhere safe.
- **Caching private responses.** A caching mistake can serve one user's private page to another. Keep caching off unless a route's target sets `Cache-Control` correctly, and never cache responses that depend on who is signed in.
- **Compression over HTTPS.** Enabling compression on a route whose responses contain secrets (e.g. CSRF tokens) next to attacker-influenced text exposes it to the BREACH attack. Enable it only for routes that serve static or public content.
- **Exposed stream ports.** A TCP or UDP route publishes a raw service, such as a database, directly to the internet, with none of the HTTP protections (no TLS added by Apiary, no HTTP-level checks). Restrict stream routes with IP allowlists wherever possible. UDP allowlists check the datagram's source address, which an attacker can forge: they keep out replies, not requests, and an open UDP route reflects the target's replies (and any amplification, e.g. DNS or NTP) to forged addresses.
- **Rate limits are per replica and per address.** A route's rate limit and the admin port's limit on anonymous requests count each client address (IPv6 per /64) on each replica, so a client spread over several replicas gets that many times the limit, and an attacker with many addresses (e.g. a botnet) isn't slowed down. Behind a proxy or Swarm's ingress network, every client shares one address and budget. They slow down password guessing and casual floods, not a distributed attack: put a DDoS protection service or a cloud firewall in front of Apiary for that.
- **Personal data in logs.** Access logs contain client IP addresses, which are personal data under the GDPR. Logging them in full by default, on the grounds of network security, was signed off by the data protection officer on 2026-11-02. Each deployment still sets how long its log pipeline keeps them, and who can read them. Revisit the sign-off if logs start being used for anything other than security and operations.
- **Let's Encrypt limits.** Bugs that request certificates in a loop can lock a domain out of new certificates for days. Test against the [staging environment](https://letsencrypt.org/docs/staging-environment/) first.
